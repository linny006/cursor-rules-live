## LANGUAGE CONTRACT

```
Reply in the chat:                     the language the human wrote in. Detect it; never assume one.
Working artifacts (docs/artifacts/*):  English, unless the project declares DOCS_LANGUAGE.
Code (identifiers, comments, commits, logs, error codes):  English — always. No exceptions.
Product UI strings / user-facing text: the language of THAT product's users — declared in BUSINESS_LOGIC.md.
The role system itself (.cursorrules, roles/*.md):  English — do not translate back.
```

**The language of the instructions does NOT set the language of the reply.** The system is written in English
because the artifact layer is read by the model far more often than by a person; the reply follows the human.
**Law 44 owns this contract** — the reasoning, the `DOCS_LANGUAGE` override and the carve-out for the product's
own strings are stated there in full. This block is the operative summary, not a second decision.

## TASK ROUTING (the first action of every task)

Before any role acts, the task's **class** is resolved and that class's minimum is opened from **`roles/RAG_CANON.md` §2 — the Task Router**. Normally @LEAD resolves it. **When the user addresses roles directly without @LEAD, the first role addressed resolves the class itself**, opens the minimum, and opens its reply with one line: `CLASS: TC-xx · COST: tier=Ex` (Law 43). The router states, per class: what must be read, in what order, and — where the distinction matters — what is deliberately out of scope.

```
Task → @LEAD → resolve class (roles/RAG_CANON.md §2) → read the class minimum
     → LPA (Law 24) → PRE-PLAN GATE → the CHAIN PROTOCOL below
```

**The router is a priority order, not a whitelist.** It declares what MUST be read first and in what sequence; the rest of the library stays available and is opened on demand. A role that needs a file outside its class minimum opens it and names it in the report — that is normal work, not a deviation. Narrowing the agent's field of view is not the goal; removing the guesswork about *where to start* is.

**Three levels, cascading — not three competing lists.** `.cursorrules` holds the **laws**. `roles/RAG_CANON.md` §2 holds the **task class** and its cross-cutting minimum. The acting role's own **reading map** holds the **detail inside that role's domain** (`roles/ROLE_DESIGN.md` and `roles/ROLE_FRONTEND.md` carry one; other roles gain theirs as their domains require). Each level narrows the one above it; where two levels name the same canon, **the more specific section pointer wins**. A role's map may add a file the class does not name; it may not drop one the class names. This is a tree, not a switch — the constitution does not enumerate every file, the class does not either, and the role knows its own.

**Roles are composed, never assigned.** Classes and role sets in this system are **defaults that remove the blank page**, never permission lists. The developer combines roles for the situation — two, five, or a pairing no table names — and that composition is an instrument of the work. Nothing in the routing layer may narrow it, and no role is ever excluded because a table did not list it.

**Registration rule — a canon that is not in the router does not exist.** Any change that **adds, renames, merges, retires or repurposes** a `roles/*.md` file updates `roles/RAG_CANON.md` §2 **in the same change** (the operations and the drift check with its trigger live in that file's §6 — this is the pointer, not a second copy) (`roles/SYSTEM_EVOLUTION_PROTOCOL.md`, `@EVOLVE`). An unrouted file is dead text: it will not be read, and its rules will not hold.
