# UX Review & Persona Walkthrough Rules (ISO 9241 / CPUX)

When asked to review UX, improve usability, create/save personas, design a user flow, write usability test tasks, or build/refactor a UI component (`*.html`, `*.twig`, `*.vue`, `*.tsx`, `*.jsx`, `*.svelte`, `*View.java`):

1. **Persona Discovery, Persistence & Cognitive Walkthrough (Route A — Existing UI):**
   Check if `docs/ux/personas.md` exists in the repository and reuse those project personas. Otherwise, define 1 Primary Persona (task-focused, realistic context constraints like mobile use, glare, gloves, or time pressure) and 1 Edge-Case / Accessibility Persona (keyboard-only `Tab`/`Enter`/`Esc`, screen-reader, or 200% zoom) and trace their step-by-step path through the interface. When asked to create or save personas for project-wide reuse, persist them in `docs/ux/personas.md`.

2. **5-State Completeness Check:**
   Never ship Happy-Path-only UI. Verify and implement all 5 states:
   - `Empty State`: Motivating explanation why it is empty + direct primary Call-to-Action (CTA).
   - `Loading State`: `aria-busy="true"` on container, disabled submit trigger to prevent double-submits, layout-stable skeleton/spinner.
   - `Error / Offline State`: **Preserve all valid user input!** Never call `form.reset()` on validation error. Provide inline field recovery via `aria-invalid="true"` and `aria-describedby`, plus `role="alert"` summary.
   - `Partial / Overflow State`: Handle long German compound words (`break-words`/`hyphens: auto`), large lists, and missing optional data gracefully.
   - `Success State`: Clear feedback (`role="status"`, `aria-live="polite"`) + inline **Undo** or explicit verb-based confirmation dialog (`"Mitglied löschen"` vs. `"Abbrechen"`, never `"OK/Cancel"`) for destructive actions.

3. **ISO 9241-110:2020 Interaction Principles:**
   - *Aufgabenangemessenheit (Suitability for the user's tasks):* Smart defaults/presets for the 80% case, `autocomplete`, `inputmode="numeric|tel"`.
   - *Selbstbeschreibungsfähigkeit (Self-descriptiveness):* Persistent `<label for="...">` (never placeholder-only inputs), visible format hints linked via `aria-describedby`.
   - *Erwartungskonformität (Conformity with user expectations):* Semantic `<button type="button|submit">` instead of `<div onClick>`, native `<dialog>`, logical `Tab` focus order.
   - *Erlernbarkeit (Learnability):* Progressive disclosure for advanced settings.
   - *Steuerbarkeit (Controllability):* Back-navigation without data loss, respect `@media (prefers-reduced-motion: reduce)`, use scalable `rem` units.
   - *Robuste Verwendung (Use error robustness):* Forgiving input parsers that strip spaces/formatting automatically (e.g., `.replace(/\s+/g, '')` on IBANs/phone numbers), plausibility limits, and destructive action guardrails.
   - *Benutzerbindung (User engagement):* Trustworthy micro-copy, zero dark patterns, motivating empty states.

4. **New Feature Conception — Problem vs. Solution Space (Route B — ISO 9241-210):**
   Structure new feature concepts into 4 strictly separated sections:
   - **1. Context of Use, Persona & As-Is Scenario (*Nutzungskontext, Persona & Ist-Szenario*)**
   - **2. User Needs (*Erfordernisse* — Problem Space):** Format as `"Als [Persona] benötige ich [Voraussetzung], um [Ziel zu erreichen]."` Never mention concrete UI widgets ("dropdown", "modal", "button") in this section!
   - **3. User Requirements (*Nutzungsanforderungen*):** Qualitative requirements + measurable ISO 9241-11 Quantitative targets (Effectiveness, Efficiency, Satisfaction).
   - **4. To-Be Walkthrough (*Soll-Szenario*) & Interaction Concept:** Concrete UI architecture, physical ergonomics, and all 5 UI states.

5. **Non-Leading Usability Test Tasks (Route C — CPUX Evaluation):**
   When writing tasks for usability test participants, embed them in a realistic scenario with concrete data and a verifiable end state, and **never quote literal UI labels** (menu items or button names) in the participant task text.
