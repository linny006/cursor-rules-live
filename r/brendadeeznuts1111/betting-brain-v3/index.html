## Core Development Rules

### Bun Runtime (CRITICAL)
- Use `bun` commands exclusively (not npm/yarn/node)
- Use Bun Test (not Vitest/Jest)
- Use Bun file APIs (not Node.js fs)
- Use processManager for all process spawning
- Leverage Bun native APIs (crypto, compression, etc.)

### File Organization
- Root directory: Only 9 essential files allowed
- Documentation: All docs in `docs/` (except README.md, LICENSE, CLAUDE.md)
- Scripts: All in `scripts/`
- Tools: All in `tools/`
- Status files: All in `docs/`

### File Naming
- Use lowercase kebab-case for all files/directories
- Test files: `*.test.ts` (preferred)
- Special cases: MCP handlers use camelCase to match tool names
- Never create backup files (*.backup, *.old, *.bak)

## API & Endpoint Patterns

### Request Handling
- Always generate requestId: `Date.now().toString(36)`
- Always include CORS headers for dashboard access
- Always handle OPTIONS preflight requests
- Always log with requestId prefix: `[${requestId}] ...`

### Error Handling
- Use standardized error classes from `src/utils/error-handler.ts`
- Always use try-catch or asyncHandler wrapper
- Always return structured error responses
- Never expose internal details in error messages

### Database Queries
- Always use parameterized queries (`.bind()`)
- Never use string interpolation in SQL
- Always cast D1 results with `as unknown as`
- Always handle database errors

## Security Patterns

### Input Validation
- Always validate all inputs before processing
- Use Zod schemas for request validation
- Never trust user input
- Always sanitize output to prevent XSS

### Production Security
- Never use `parseFloat()` on stakes (use `Number()`)
- Always use parameterized D1 queries
- Respect queue batch limits (100 messages max)
- Always free WASM memory in finally blocks
- Use explicit UTC timestamps (not `new Date()`)

## Testing Patterns

### Bun Test Usage
- Import from `bun:test` (not vitest/jest)
- Always cleanup processes in `afterEach`/`afterAll`
- Use `{ results: [...] }` for D1 database mocks
- Reset mock implementations in `beforeEach`
- Use explicit try-catch for async error testing

### Test Organization
- Unit tests: `tests/unit/*.test.ts`
- Integration tests: `tests/integration/*.test.ts`
- Use descriptive test names
- Group related tests in `describe` blocks

## Cloudflare Workers

### Environment Bindings
- ANALYTICS: Main betting analytics database
- KV namespaces: BET_TICKER_RAW, TOKEN_STORE, USER_STORE
- Queues: LINE_INGRESS, STEAM_WEBHOOK, STEAM_QUEUE
- Analytics Engine: ANALYTICS_ENGINE

### Performance
- CPU limit: 50ms per request
- Use `ctx.waitUntil()` for non-blocking operations
- Implement cost guards for resource limits
- Use rate limiting (10 req/s per IP)

## MCP Integration

### MCP Server Patterns
- Use JSON-RPC 2.0 protocol over stdio
- Register tools with `registerTool(name, description, inputSchema, handler)`
- Return MCP response format: `{ content: [{ type: 'text', text: '...' }] }`
- Use standard JSON-RPC error codes (-32700 parse, -32600 invalid, -32601 method not found, -32602 invalid params, -32603 internal)
- Never use external MCP SDK if Bun + Zod suffices

### Tool Development
- Create handler in `src/mcp/handlers/`
- Register in `toolRegistry.ts`
- Define in `tools.ts` with schema
- Always validate args before database queries
- Return `MCPToolResult` format

### Sports API Validation
- Validate all sports data with Zod schemas
- Required fields: eventId, timestamp, metric, value
- Use metadata for market, source, volume
- Write to ANALYTICS_ENGINE with proper blobs/doubles/indexes
- Handle CORS for cross-origin requests

### Testing MCP Tools
- Use direct handler testing first
- Test with `bun scripts/test-handlers-direct.ts`
- HTTP testing via `/mcp` endpoint

## Sports API Integration

### Data Fetching
- Use MCP `live-odds` tool for odds (never hard-code API calls)
- Aggregate ≥ 2 bookmakers for accuracy (Pinnacle + Bet365)
- Cache live data ≤ 30s in SPORTS_CACHE KV
- Sports enum: nba, nfl, mlb, nhl only
- Markets enum: moneyline, spread, total only

### Data Ingestion
- Push via `push-sports-data` MCP tool after every fetch
- Ingest endpoint requires JWT signed with JWT_SECRET
- Rate limit: 100 req/min per IP on `/ingest`
- Validate eventId, timestamp, odds (required fields)
- Include source and volume in metadata

### API Key Rotation
- Use rotateSecret() for daily key rotation
- Pattern: PINNACLE_KEY_1, PINNACLE_KEY_2, PINNACLE_KEY_3
- Rotation based on day of year % 3 + 1
- Never commit actual keys to repo
